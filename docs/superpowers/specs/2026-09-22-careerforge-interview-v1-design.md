# CareerForge-AI 面试优先版设计

状态：待用户审阅。本文记录已确认的产品与架构边界，不表示功能已实现。

## 1. 目标与交付边界

目标是做出可由新用户独立、流畅使用的作品集级模拟面试产品，而不是继续扩充旧的求职训练链。首版只支持「AI Agent 开发」一个岗位方向；方向选择保留为扩展点，不再拆成「Java AI 应用开发」与「Java Agent 应用开发」。快速面试的“快速”指准备过程快，不指 15～20 分钟结束。

分两次交付，分别验收：

1. **快速面试**：注册、登录、选择方向、准备与确认、正式面试、报告、历史记录与恢复，形成独立可用闭环。
2. **综合面试**：在共用基础能力上增加 JD、薪资范围、简历与个人描述、解析确认、时长和难度设置、个性化主题与报告；交付时同时回归快速面试。

首版不接入支付；不做 15～20 分钟演示线、语音/视频回答、扫描件/图片/OCR、复训计划、个人证据库、实时评分、用户自助维护公共题库。历史立项评估与第二阶段需求分析不再作为新业务实现依据。旧代码暂留，待新流程稳定后另行决定清理范围；旧面试页面及 `/api/mock-interviews` 等旧面试接口不得向普通用户开放。旧用户面试数据为测试记录，不迁移到新流程；现有向量库保留。

## 2. 两条业务线

| 规则 | 快速面试 | 综合面试 |
| --- | --- | --- |
| 用户准备 | 登录后选择 AI Agent 开发方向 | 选择方向，填写 JD 和薪资范围；可上传简历、填写个人描述 |
| 简历 | 不要求 | PDF、DOCX；扫描件/图片/OCR 不支持。解析后展示可编辑画像，用户确认后使用 |
| 时长 | 固定 60 分钟有效作答时间 | 选择 60 或 90 分钟有效作答时间 |
| 难度 | 不增加选择步骤，使用默认难度 | 基础、标准、挑战三级 |
| 主体覆盖 | 8 个预定考查目标，每目标一道主问题 | 6 个覆盖不同能力面的主题，每主题一道主问题 |
| 追问上限 | 全场最多 4 次 | 60 分钟最多 4 次；90 分钟最多 8 次 |
| 单环节追问 | 最多连续 2 次 | 最多连续 2 次 |
| 题目依据 | 管理员维护的公共面经资源，经 RAG 检索、质量筛选和变化问法 | JD、薪资范围、经确认的本次画像、公共面经资源和 RAG；有足够经历信息时，6 个主题中安排 2～3 个经历相关主题，其余覆盖岗位核心能力 |

简历与个人描述是本次面试的**不可信画像输入**，不是事实认证或用户能力结论；薪资范围只用于岗位预期和问题层次的参考，不能推断真实能力。简历没有提供或没有解析出有效经历时，平台用 JD 和岗位能力设置主题，不生成假岗位、假经历或假证据。提取字段包括个人描述、核心技能、项目经验、工作经验和实习经验；缺失字段留空，不能让模型补造。原始上传文件仅用于解析，不作为长期保存的个人证据库；保留用户确认过的本次面试画像快照以支持出题、报告和历史回看。

岗位方向在首版仅有 AI Agent 开发。具体主题、考查目标和计划追问不向用户展示，避免提前泄题；面试中仅展示当前题目、必要的进度和时间、回答与操作控件，不展示实时评分或内部评审过程。

## 3. 用户旅程与生命周期

两条业务线都采用「填写信息 → 准备面试 → 已就绪确认页 → 正式开始」的两段式启动。准备时生成覆盖计划及首批合格问题；用户可在确认页开始，或返回修改输入。修改任何用于出题的输入都会使旧准备结果失效并重新准备。准备中、已就绪、面试中和报告生成中的会话均可从用户的面试入口或历史列表重新进入。每名用户同一时间最多有一场尚未结束作答的面试；已结束作答、正在生成报告的会话不占用这个名额。

新会话的业务状态至少区分：`DRAFT`、`PREPARING`、`READY`、`ANSWERING`、`WAITING_NEXT`、`PAUSED`、`GENERATING_REPORT`、`REPORT_READY`、`REPORT_RETRYABLE`、`CANCELLED`。这些是新业务状态，不复用旧 `InterviewStatus`；实现时可将页面可见状态与内部任务状态拆开，但必须保留等价业务语义。暂停不是终态。每次转换都校验当前用户、会话版本、合法前置状态和幂等请求标识。

正式开始后，一次只展示一道题。用户编辑文字、粘贴内容、提交或跳过；草稿自动保存，并明确显示「保存中／已保存／保存失败」。提交成功的前提是后端已经持久化且冻结答案，提交后不可修改；跳过也作为明确结果持久化。用户重新进入时恢复最后**经服务端确认**的草稿、当前题目、已提交记录与剩余有效时间；未成功发送的最后几个字不能承诺恢复。回答上限首版暂定 8000 字，测试长回答后再调整；非空回答不设最低字数。

正常答完进入报告生成。用户提前结束时，至少已有一道正式提交的答案才生成部分报告；零答案退出不生成报告。部分报告必须明确其覆盖范围，未作答或未覆盖的主题不能被写成能力缺口。报告生成时用户可以离开、切换页面或继续使用站内其他功能。历史列表可删除本人新流程的单场记录：用户二次确认后停止该会话的后台任务，并删除对应的新业务输入、问答和报告；不得波及其他面试、旧数据或公共题库。

## 4. 有效作答时间

60／90 分钟是服务端累计的**可作答时间**，不是从开始时刻到结束时刻的墙钟差。当前题目可见且允许作答才累计；提交后的分析、生成下一题、报告生成、用户主动离开、页面关闭或切到其他标签页均暂停。用户返回后先恢复现场，再继续计时。前端负责可见性事件和心跳，服务端保留累计值与最后确认时间；异常关闭后按最后有效心跳收敛，允许几秒误差，但不能信任客户端自报的总时长。

切页时暂停并给予简短提醒，说明面试建议保持专注；不禁止用户使用外部文本编辑或语音转文字工具后粘贴答案。有效时间归零时不再发新题，但允许用户完整回答当前已经展示的题；若此时离开，返回仍可完成同一题。答题框、提交和跳过操作不能因为倒计时到零而突然消失。

## 5. 出题与 RAG

准备阶段确定覆盖目标，但不把全部问题和追问一次性固定。快速面试覆盖 8 个目标；综合面试覆盖 6 个互补主题。公共面经由管理员审核维护，用户的 JD、简历、描述、答案、报告均不得自动写入公共题库或公共向量库。两条业务线都使用现有 RAG 能力检索相关面经，保留来源及片段标识供内部审计；检索结果只是参考素材，不能直接作为用户事实或模型指令。没有可靠检索时不伪造来源。

主问题可在前一题作答期间滚动预生成，以减少提交后的等待；它只能使用当时已冻结的上下文，不能假装已考虑当前未提交的答案。当前答案提交后再决定是否追问、进入下一主题或结束。追问围绕本题回答加深，不额外占用预定主题数，受单环节和全场上限约束。若预生成题与刚提交的答案重复或冲突，丢弃并重新生成，接受必要等待。题目需经结构、主题匹配、重复与安全校验才可展示；同一快速面试线尽量避免频繁原题重复，可变化问法，但不刻意跨快速/综合业务线回避同类主题，以免损害覆盖面。跨业务线共用历史去重不纳入两次交付。

准备阶段应有合格主问题和受控备用题；建立管理员维护的备用主问题集是第一交付的一部分，不能假定现有向量库天然满足此条件。快速面试在模型或检索暂不可用时可使用该备用题继续，不伪称其为实时个性化生成。综合面试若无法完成合格的个性化准备，保留输入并重试，不悄悄降级成通用面试，也不展示虚假的「已就绪」。

## 6. 已提交答案、后台任务与故障恢复

「保存并冻结答案」与「生成下一题」是两个独立边界。提交成功后立即停止有效作答计时；后台异步分析答案，决定追问、主问题或结束，再生成和持久化下一题。用户看到的是准备下一题的等待状态，不重复提交同一答案，也不因后台耗时扣减有效时间。

后台调用采用有上限的超时和重试；每一步带会话、题目和步骤标识，重试不得重复保存答案、重复扣时间、重复创建题目或跳过既定覆盖目标。可选追问生成失败时，若已有通过质量校验的下一道主问题，记录故障原因并继续下一主题；否则保持 `WAITING_NEXT`，暂停计时、保留现场、继续受控重试并允许用户离开。故障导致的追问缺席不计为用户不足。不能通过无限等待、无限重试或假问题掩盖持续故障。

报告失败只重试报告未完成的步骤，不重新执行面试提问或改写冻结答案。用户可在历史列表看到生成中、可重试或已完成状态；成功报告冻结。异常必须分清输入错误、权限拒绝、模型/检索暂不可用、处理超时和持久化失败，并给用户可理解的下一步。

## 7. 报告契约

面试结束后冻结题目、答案、跳过记录、实际覆盖主题、模式和输入快照。报告后台按环节评估：一道主问题及其追问组成一个环节，分别生成可恢复的环节结果；最后做全场校对，识别后续回答对前序不足的补充，消除互相矛盾的结论。此设计避免把多道复杂题和长回答压成一次模型调用；旧流程曾发生报告输出截断以及后续回答未消解前序缺口的 Bad Case，两个风险都必须进入新回归集。

最终报告不提供数字分数。它包含总体表现、具体优势、优先改进项和逐环节复盘；逐环节呈现原题、用户完整答案、可回链到原答案的准确引用、成立的具体点评、改进建议与必要示例。引用确实存在于原文只是最低校验条件，点评是否成立仍需人工样本和回归评测。没有依据就不强行写负面批评；跳过题、未覆盖主题和故障省略的追问不得作为能力缺陷。纯技术题未要求个人经历时，不因没有讲项目故事而扣帽子。

报告生成中只显示状态和进度，不显示可能被全场校对推翻的半成品。只有必需的环节结果和全场校对均成功后才发布最终报告；失败结果保持可重试，不能展示为成功报告。

## 8. 架构、接口与事实源

在现有 Spring Boot 项目内增加独立的新面试业务模块，不以假 `TargetRole`、假个人证据或兼容旧 Graph 状态机驱动新流程。新模块拥有独立的会话、输入快照、主题计划、题目、草稿、答案、有效时间、后台步骤和报告事实；MySQL 是事实源。Redis/短期事件流可承载安全进度和恢复提示，不承载唯一业务事实；向量库仅用于公共面经检索。新流程复用现有认证、模型网关、RAG 检索和基础观测设施中可用的部分，但复用需通过新业务接口，不继承旧流程的个人证据/Memory/训练计划前置条件。当前源码未见可直接复用的 PDF/DOCX 简历解析服务，这属于第二交付新增能力，不能写成现有功能。

新 REST API 与 `/api/mock-interviews` 分离，覆盖准备、读取准备状态、修改输入、正式开始、读取当前题、保存草稿、提交/跳过、暂停/恢复、结束、获取列表/详情/报告及报告重试。所有读取、写入、后台任务和下载/解析结果都校验登录用户对会话的归属；服务端拒绝普通用户访问旧面试接口，仅隐藏旧页面不算完成。页面刷新或事件流断开后以 REST 和 MySQL 当前状态收敛，不依赖单条 SSE 事件决定事实。

用户上传的简历、JD 和粘贴答案均是不可信输入，需做类型/大小/字符范围与权限校验，并与系统提示词、工具描述隔离。模型输出需做结构、数量、所属主题、来源、引用和可持久化状态校验；模型不能自行改变用户权限、会话时长、提交状态或公共题库。日志和追踪可记录步骤、延迟、Token、错误类型与来源标识，不记录原始简历全文、令牌或敏感回答正文。

## 9. 验收与两次实施计划

第一交付的完成条件是：一个新注册用户无需手工数据库/API 操作即可在真实浏览器中走通快速面试的准备、确认、8 个考查目标、允许范围内的追问、暂停恢复、提交、报告和历史回看；至少有真实模型与真实 RAG 的端到端证据。第二交付以同样标准走通综合面试的 JD、薪资、PDF/DOCX 解析预览与确认、60/90 分钟及难度选择、个性化 6 主题、报告，并回归第一交付。固定输入或 Mock 结果只证明局部逻辑，不冒充真实模型质量或完整用户体验。

自动化验证至少覆盖状态合法迁移、owner 隔离、重复提交/跳过、草稿恢复、切页/关闭后的计时、时间归零仍可完成当前题、准备失败与保留输入、出题/追问失败的安全继续、报告部分失败与重试、报告引用有效性，以及旧接口对普通用户的拒绝。使用可控时钟测试 60/90 分钟计时边界，真实浏览器跑完整业务流程；不得把短时跑通说成完整 60/90 分钟真人面试已实测。综合面试还需验证简历缺失字段留空、无简历降级、私有输入不进入公共题库、后续补答消解前序缺口。

实施计划应拆成两份：先完成并验收快速面试，再增加综合面试及回归。每份计划列出数据库迁移、后端接口、前端页面、模型/RAG 契约、自动化测试与真实端到端验收；设计文档获批前不进入计划和编码。

## 10. 已知取舍与非目标

- 为缩短答题间等待，允许滚动预生成下一道主问题；因此它可能未利用当前未提交的答案，提交后必须检查重复和冲突。
- 为保持流畅，模型故障时可放弃可选追问；但不得丢失已提交答案、扣除等待时间或假装用户未答。
- 为守住综合面试的个性化承诺，准备失败时可等待和重试，不用通用题冒充完成。
- 报告按环节分批再全场校对，生成时间可能长于单次调用；用户可离开，报告只在完成后发布。
- 原有向量库和旧代码暂保留；旧业务数据不迁移，旧用户入口关闭。删除旧代码、旧表或旧数据不属于本设计授权范围。
